# Многозадачность (concurrency)
1. Общая архитектура

Система построена по микросервисному принципу: каждый сервис изолирован, имеет:

собственную БД;

независимый жизненный цикл;

чётко определённый API.

Ключевые принципы:

Слабая связность — сервисы взаимодействуют через API/сообщения, без прямых SQL‑запросов к чужим БД.

Отказоустойчивость — репликация БД между ЦОД, мониторинг, автоматическое восстановление.

Масштабируемость — горизонтальное масштабирование сервисов и БД.

2. Инфраструктура данных
2.1. Кластеризация БД

Каждая сервисная БД развёрнута в кластере (минимум 2 ЦОД).

Технология: Patroni (для PostgreSQL) или аналоги (например, MongoDB Replica Set, MySQL InnoDB Cluster).

Репликация: синхронная/полусинхронная для минимизации потерь данных.

2.2. Резервное копирование

Ежедневные бэкапы с хранением в S3‑хранилище.

Возможность быстрого восстановления (point‑in‑time recovery).

2.3. Доступ к данным

Сервисы работают только со своей БД.

Для чтения данных из других сервисов — API или Kafka‑события.

3. Асинхронное взаимодействие
3.1. Брокер сообщений

Используется Apache Kafka (или аналог: RabbitMQ, NATS).

Сценарии:

Отправка уведомлений (сервис «Нотификации» слушает события из Kafka).

Обновление статуса заказа (сервис «Заказы» публикует событие → сервис «Платежи» реагирует).

Модерация отзывов (сервис «Отзывы» отправляет на проверку → сервис «АРМ администратора» обрабатывает).

3.2. Паттерны

Event Sourcing — изменения состояния сохраняются как последовательность событий в Kafka.

CQRS — разделение операций чтения и записи (например, для сервиса «Товары»).

Saga — координация длительных транзакций между сервисами (например, отмена заказа с возвратом платежа).

4. Мониторинг и observability
4.1. Технический мониторинг

Инструменты: Grafana + Prometheus (или целевой стек компании).

Метрики:

Загрузка CPU/памяти сервисов.

Время отклика API.

Количество ошибок (HTTP 5xx).

Задержка репликации БД.

Состояние Kafka (lag, throughput).

4.2. Бизнес‑метрики

Сбор данных через ежедневную репликацию в аналитическое хранилище (например, ClickHouse).

Визуализация: FineBI (или Tableau, Power BI).

Примеры метрик:

Количество заказов в час.

Средний чек.

Конверсия в оплату.

Активность пользователей в геймификации.

5. Описание сервисов
5.1. Платежи

Функции: проведение платежей, хранение истории, возврат средств.

БД: PostgreSQL (кластер).

Асинхронность:

Слушает Kafka‑события «Заказ создан» → инициирует платёж.

Отправляет события «Платеж выполнен» → триггер для сервиса «Заказы».

5.2. Заказы

Функции: создание, отмена, изменение статуса.

БД: PostgreSQL (кластер).

Конcurrency:

Пул потоков для обработки API‑запросов.

Kafka‑продюсер для событий статуса заказа.

5.3. Нотификации

Функции: отправка email/SMS/push.

БД: PostgreSQL (хранит шаблоны и историю).

Асинхронность:

Потребитель Kafka‑событий (например, «Заказ оплачен»).

Очередь задач для отправки (Redis/RabbitMQ).

5.4. Товары

Функции: CRUD товаров, управление остатками.

БД: PostgreSQL (кластер с репликой для чтения).

Concurrency:

Кэширование (Redis) для часто читаемых данных.

Отдельные потоки для обновления остатков.

5.5. Отзывы

Функции: модерация, рейтинг, отображение.

БД: PostgreSQL (кластер).

Асинхронность:

События Kafka при создании отзыва → триггер модерации.

5.6. Лояльность

Функции: расчёт скидок, управление программами.

БД: PostgreSQL (кластер).

Concurrency:

Периодические задачи (cron) для обновления статусов программ.

5.7. Обращения

Функции: приём, маршрутизация, закрытие обращений.

БД: PostgreSQL (кластер).

Асинхронность:

Kafka‑события при создании обращения → триггер уведомлений.

5.8. АРМ администратора

Состав: UI (React), backend (Node.js/Python), БД (PostgreSQL).

Функции: редактирование контента, управление заказами, модерация.

Concurrency:

Многопоточность для обработки админ‑запросов.

Веб‑сокеты для уведомлений в UI.

5.9. Датчики

Функции: сбор, хранение, анализ данных с датчиков.

БД: TimescaleDB (кластер) для временных рядов.

Concurrency:

Потоковая обработка данных (Kafka Streams).

5.10. Профили пользователей

Функции: хранение и обновление данных пользователей.

БД: PostgreSQL (кластер).

Concurrency:

Кэширование (Redis) для быстрого доступа.

5.11. Геймификация

Функции: начисление баллов, уровни, награды.

БД: PostgreSQL (кластер).

Асинхронность:

События Kafka при действиях пользователя → расчёт баллов.

5.12. Новости

Функции: публикация, категоризация, отображение новостей.

БД: PostgreSQL (кластер).

Concurrency:

Кэширование страниц (CDN + Redis).

5.13. Сеть

Функции: чаты, сообщения, уведомления.

БД: PostgreSQL (кластер).

Concurrency:

WebSocket‑соединения для онлайн‑чата.

Очереди сообщений (Kafka) для офлайн‑доставки.

5.14. Тренировки

Функции: планирование, отслеживание прогресса.

БД: PostgreSQL (кластер).

Concurrency:

Фоновые задачи для напоминаний.

6. Механизмы concurrency
6.1. На уровне сервисов

Многопоточность (threads) — для CPU‑bound задач (расчёты в «Лояльности»).

Асинхронные фреймворки (asyncio, Node.js) — для I/O‑bound (API‑запросы).

Worker Pools — фиксированное число потоков для обработки очередей.

6.2. На уровне БД

Connection pooling (PgBouncer).

Read replicas для масштабирования чтения.

Оптимистичная блокировка (versioning) для конкурентных обновлений.
6.3. На уровне инфраструктуры

Kubernetes: автомасштабирование подов (Horizontal Pod Autoscaler).

Load balancing (Nginx, HAProxy).
